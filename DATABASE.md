# Database

PostgreSQL 16 is the **single source of truth** for everything persistent.
Redis only holds ephemeral data (presence, pub/sub, rate-limit counters) that
can be lost without consequence.

Schema source: [`packages/db/src/schema.ts`](packages/db/src/schema.ts) (Drizzle ORM).
Migrations: [`packages/db/migrations/`](packages/db/migrations) (generated SQL, committed).

## Conventions

| Topic                       | Convention                                                                                                                                                  |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary keys                | `uuid`, **UUIDv7** generated by the application: time-ordered (good index locality), not guessable, safe to expose to clients, can be created before insert |
| Naming                      | `snake_case` tables (plural) and columns                                                                                                                    |
| Time                        | `timestamptz` everywhere, UTC; `created_at`, `updated_at` on mutable tables                                                                                 |
| World scoping               | Every in-world entity carries `world_id`, even though there is one shared world today                                                                       |
| Deletion                    | Soft delete (`deleted_at`) for entities the world's history may reference (characters); hard delete for purely technical rows (sessions)                    |
| Enums                       | Stored as `text`, validated by zod in the application. Easier to evolve than PostgreSQL enums. CHECK constraints can be added once values stabilise         |
| JSONB                       | Only for data whose shape is expected to evolve and that we never join or constrain on (appearance, event payloads). JSON documents carry a `version` field |
| Integrity                   | Uniqueness and relations are enforced by constraints, not application checks                                                                                |
| Money / quantities (future) | Integers in the smallest unit (`bigint`), never floating point                                                                                              |

## Entity relationships (phase 1)

```
accounts 1───* sessions
    │
    1
    │
    *
characters *───1 worlds 1───* world_events
                                  │  ▲
                                  │  └── actor_account_id  → accounts   (nullable)
                                  └───── actor_character_id → characters (nullable)
```

- An **account** is the real person's login (out-of-game identity).
- A **character** is an in-game identity. An account owns many characters
  (limit `MAX_CHARACTERS_PER_ACCOUNT`, default 5) but **plays only one at a
  time**. This is enforced in real time by the gateway, not by the schema,
  because it is a property of the live connection.
- A **world** is the shared persistent world. One row today (`slug = main`).
- **World events** are an append-only log of meaningful happenings.

### `world_events`

| Column             | Type             | Notes                                                      |
| ------------------ | ---------------- | ---------------------------------------------------------- |
| id                 | uuid PK          | UUIDv7 → naturally time-ordered                            |
| world_id           | uuid FK → worlds | index `(world_id, created_at)`                             |
| type               | text             | dotted type, e.g. `character.created`, `character.deleted` |
| actor_account_id   | uuid FK null     | set null on delete                                         |
| actor_character_id | uuid FK null     | set null on delete                                         |
| payload            | jsonb            | event-specific data                                        |
| created_at         | timestamptz      |                                                            |

Purpose: audit trail today; tomorrow the world's **history and chronicle** (who
founded what, which battle changed which border) and the input for systems that
react to player actions. It is **not** event sourcing: current state lives in
normal tables, and events are written in the _same transaction_ as the change
they describe.

## Persistence strategy

1. **Write-through, transactional.** Every player action that changes durable
   state commits to PostgreSQL before anyone is told about it. There is no
   "in-memory world that is flushed periodically", so there is no data loss on
   crash.
2. **Ephemeral in Redis.** Presence, bus messages and rate-limit counters only.
   Losing Redis disconnects players briefly; it never loses game data.
3. **Hot data in memory is allowed later** (e.g. a combat instance or an awake
   region cached by the worker), but it is always reconstructible from
   PostgreSQL and checkpointed after each meaningful step (e.g. after each
   combat turn).
4. **Migrations** are generated from the schema (`pnpm db:generate`), reviewed
   and committed, and applied by `migrate.js` before a release. Prefer
   additive, backward-compatible migrations (add column → deploy → backfill →
   tighten), so old and new server versions can run side by side during a
   rolling deploy.

## Growth path

| Pressure                   | Response                                                                                                             |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Read load                  | Read replicas for non-critical reads (leaderboards, history); caching in Redis                                       |
| `world_events` volume      | Native partitioning by month on `created_at`; archive old partitions                                                 |
| Hot tables (items, ledger) | Proper indexes, `bigint` counters, and batching in the worker                                                        |
| Many worlds/shards         | Already modelled (`world_id`); a separate database per world cluster is possible because nothing joins across worlds |
| Connection count           | PgBouncer in transaction mode in front of PostgreSQL                                                                 |
